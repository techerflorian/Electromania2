Rapport d'audit du projet ElectroMania
======================================

Date de l'audit : 30/06/2026
Projet audite : ElectroMania
Type de projet : application PHP MVC avec framework maison


1. Cadre de l'audit
-------------------

Cet audit est un audit statique du code source. Il porte sur :
- la structure du projet ;
- la securite applicative ;
- la logique metier ;
- la base de donnees ;
- la qualite du code ;
- les points de maintenance.

Verification effectuee :
- inspection des fichiers du projet ;
- recherche des usages de $_GET, $_POST, $_SESSION, SQL, CSRF et droits ;
- controle de syntaxe PHP avec PHP 8.2.12.

Limites :
- l'application n'a pas ete testee dans un navigateur ;
- la base MySQL n'a pas ete lancee pendant l'audit ;
- aucun audit de vulnerabilites externes en ligne n'a ete fait ;
- les changements deja presents dans le working tree n'ont pas ete modifies,
  sauf la creation de ce rapport.

Resultat du controle syntaxique :
- aucune erreur de syntaxe PHP detectee sur les fichiers .php audites.


2. Resume executif
------------------

Le projet est une bonne base pedagogique : la structure MVC est presente, les
modules sont separes, les classes Table centralisent une partie du CRUD, les
requetes specifiques utilisent souvent PDO prepare, les mots de passe sont
haches avec password_hash(), et une protection CSRF a commence a etre ajoutee.

En revanche, le projet n'est pas pret pour une mise en production. Les risques
principaux sont :
- des actions sensibles accessibles directement par URL ;
- un generateur de code exposable depuis le routeur ;
- une action de creation de base de donnees non protegee ;
- des suppressions faites en GET sans CSRF ;
- des controles d'autorisation incomplets ;
- plusieurs bugs dans le panier et les commandes ;
- des sorties HTML non echappees dans certains endroits.

Priorite generale :
1. Bloquer les routes dangereuses et proteger les actions sensibles.
2. Corriger les droits dans tous les controleurs, pas seulement dans le menu.
3. Corriger le panier, les suppressions et les verifications CSRF.
4. Nettoyer les sorties HTML et les messages utilisateurs.
5. Durcir la configuration et la base de donnees.


3. Points positifs
------------------

Architecture :
- structure MVC claire : application/module, application/table, framework ;
- controleur principal unique dans www/index.php ;
- gabarit commun dans application/gabarit/gabarit.php ;
- classes metier separees dans application/table ;
- modules principaux presents : article, categorie, commande, contenir,
  profil, utilisateur, authentification.

Base technique :
- PDO utilise pour la connexion principale ;
- PDO::ERRMODE_EXCEPTION active ;
- plusieurs requetes applicatives utilisent prepare() et bindValue() ;
- password_hash() et password_verify() sont utilises pour les mots de passe ;
- une classe CsrfToken existe ;
- csrfField() est present dans plusieurs formulaires ;
- .env est bien ignore par .gitignore ;
- les logs sont centralises dans framework/Logger.class.php.

Fonctionnel :
- inscription et connexion presentes ;
- catalogue par categorie ;
- recherche d'articles ;
- panier en cours d'implementation ;
- CRUD d'administration pour plusieurs tables ;
- schema SQL avec cles etrangeres principales.


4. Risques critiques
--------------------

4.1. Routeur trop permissif

Fichier concerne :
- www/index.php:14-15

Le routeur construit directement le nom de classe depuis $_GET["m"] :
- $module = "Ctr_" . $_GET["m"];
- new $module($_GET["a"]);

Probleme :
- aucun filtrage strict de m et a ;
- aucune liste blanche des modules autorises ;
- aucune verification method_exists() ;
- des modules techniques comme _generateur peuvent etre appeles si accessibles ;
- une mauvaise valeur peut produire une exception et, en mode development,
  exposer des informations techniques.

Impact :
- exposition d'actions non prevues ;
- surface d'attaque importante ;
- erreurs detaillees visibles si APP_ENV=development.

Correction recommandee :
- limiter m et a a un format strict, par exemple /^[a-z_]+$/ ;
- declarer une liste blanche des modules publics ;
- interdire _generateur, creerbdd et dataset hors environnement local ;
- verifier que la classe et la methode existent avant instanciation ;
- retourner une 404 propre si la route est invalide.


4.2. Generateur de code exposable

Fichier concerne :
- application/module/_generateur/Ctr__generateur.class.php:3
- application/module/_generateur/Ctr__generateur.class.php:69
- application/module/_generateur/Ctr__generateur.class.php:80
- application/module/_generateur/Ctr__generateur.class.php:92
- application/module/_generateur/Ctr__generateur.class.php:101
- application/module/_generateur/Ctr__generateur.class.php:109
- application/module/_generateur/Ctr__generateur.class.php:123

Le module _generateur peut creer ou ecraser des fichiers avec file_put_contents().

Probleme :
- aucune authentification dans le constructeur ;
- aucune verification que l'application est en local ;
- le routeur peut potentiellement atteindre ce module ;
- le generateur ecrit dans application/table, application/module et gabarit.

Impact :
- ecrasement de code applicatif ;
- alteration du menu ;
- creation de fichiers non voulus ;
- risque majeur si l'application est publiee.

Correction recommandee :
- retirer le module _generateur du deploiement ;
- ou le bloquer par APP_ENV === "development" et checkAllow([3]) ;
- ajouter une protection supplementaire cote routeur ;
- ne jamais exposer ce module sur un serveur public.


4.3. Creation de base de donnees non protegee

Fichier concerne :
- application/module/_default/Ctr__default.class.php:21-24

L'action a_creerbdd() execute :
- Table::creer("../document/" . DB_BDD . ".sql");

Probleme :
- aucune authentification ;
- aucune limitation a l'environnement local ;
- le script SQL contient des DROP TABLE ;
- l'action peut recreer ou vider des tables si appelee.

Impact :
- perte de donnees ;
- indisponibilite de l'application ;
- risque critique si l'URL est accessible.

Correction recommandee :
- supprimer cette action en production ;
- ou la proteger par APP_ENV === "development" et un controle admin ;
- demander une confirmation forte ;
- ne jamais laisser une action destructive accessible en GET/public.


4.4. Autorisations incompletes dans les controleurs

Fichiers concernes :
- application/module/article/Ctr_article.class.php
- application/module/categorie/Ctr_categorie.class.php
- application/module/profil/Ctr_profil.class.php
- application/module/utilisateur/Ctr_utilisateur.class.php
- application/module/commande/Ctr_commande.class.php
- application/module/contenir/Ctr_contenir.class.php

Constat :
- certains a_index() utilisent checkAllow([3]) ;
- mais a_edit(), a_save(), a_delete() et a_show() ne sont pas tous proteges ;
- le module contenir n'a pas de checkAllow() ;
- le menu masque certains liens, mais les URLs restent appelables directement.

Exemples :
- article/Ctr_article.class.php:15 protege seulement a_index().
- categorie/Ctr_categorie.class.php:15 protege seulement a_index().
- profil/Ctr_profil.class.php:15 protege seulement a_index().
- utilisateur/Ctr_utilisateur.class.php:15 protege seulement a_index().
- commande/Ctr_commande.class.php:18 protege seulement a_index().
- contenir/Ctr_contenir.class.php n'a pas de controle d'acces.

Impact :
- un utilisateur peut tenter d'appeler directement des actions admin ;
- modification ou suppression possible si les autres conditions sont remplies ;
- securite basee sur l'affichage du menu, pas sur le serveur.

Correction recommandee :
- placer checkAllow([3]) dans les actions admin elles-memes ;
- ou proteger tout le controleur dans le constructeur selon le module ;
- proteger les actions panier avec checkAuth() et verification de propriete ;
- ne jamais se limiter au masquage des liens HTML.


4.5. Suppressions en GET sans CSRF

Fichiers concernes :
- application/module/article/Ctr_article.class.php:68-74
- application/module/categorie/Ctr_categorie.class.php:68-74
- application/module/profil/Ctr_profil.class.php:68-74
- application/module/utilisateur/Ctr_utilisateur.class.php:68-74
- application/module/contenir/Ctr_contenir.class.php:67-73
- application/module/commande/Ctr_commande.class.php:77-88

Probleme :
- les suppressions utilisent $_GET["id"] ;
- il n'y a pas de verification CSRF ;
- les liens de suppression sont de simples <a href=...> ;
- une image, un lien ou une page externe pourrait declencher l'action.

Impact :
- suppression non intentionnelle ;
- faille CSRF ;
- comportement dangereux pour les donnees.

Correction recommandee :
- transformer les suppressions en formulaires POST ;
- ajouter csrfField() dans chaque formulaire ;
- verifier verifyCsrf() dans chaque a_delete() ;
- ajouter checkAllow() ou checkAuth() selon le cas ;
- verifier que l'utilisateur possede la ressource avant suppression.


5. Risques importants
---------------------

5.1. Bug dans la suppression de commande

Fichier concerne :
- application/module/commande/Ctr_commande.class.php:77-88

Le code teste :
- if ($com_statut == 1)

Probleme :
- $com_statut n'est pas defini dans cette methode ;
- avec le gestionnaire d'erreurs, cela peut declencher une erreur 500 ;
- la suppression de commande risque donc de ne pas fonctionner.

Correction recommandee :
- charger la commande depuis son id ;
- lire son statut reel ;
- supprimer seulement si le statut l'autorise ;
- sinon renvoyer un message propre.


5.2. Suppression d'une ligne de panier dirigee vers la mauvaise action

Fichier concerne :
- application/module/commande/vue_commande_edit.php:79

Le bouton de suppression d'une ligne du panier appelle :
- commande/delete avec id=$con_id

Probleme :
- $con_id appartient a la table contenir ;
- commande/delete supprime une commande, pas une ligne de panier ;
- cela peut produire une erreur ou supprimer une mauvaise donnee si les ids se
  recoupent.

Correction recommandee :
- creer une action commande/supprimerdupanier ;
- ou appeler contenir/delete avec controles d'autorisation ;
- verifier que la ligne appartient bien a la commande de l'utilisateur.


5.3. Ajout au panier incoherent depuis le catalogue

Fichiers concernes :
- application/module/article/vue_article_catalogue.php:53
- application/module/commande/Ctr_commande.class.php:135-147

Le catalogue envoie :
- commande/ajouteraupanier&id=$art_id

Mais l'action a_ajouteraupanier() utilise $_GET["id"] comme id de commande :
- $_POST["con_commande"] = $_GET["id"];

Probleme :
- le lien du catalogue passe un id article ;
- l'action attend un id commande ;
- l'action attend aussi con_quantite et con_article en POST ;
- donc le lien "Ajouter au panier" ne peut pas ajouter correctement un article.

Correction recommandee :
- utiliser la commande en cours depuis $_SESSION["com_id"] ;
- passer l'id article dans un champ explicite, par exemple art_id ;
- demander la quantite dans un formulaire POST ;
- verifier CSRF et authentification.


5.4. Modification de quantite sans verification CSRF effective

Fichiers concernes :
- application/module/commande/vue_commande_editquantite.php:11
- application/module/commande/Ctr_commande.class.php:150-164

La vue contient csrfField(), mais a_editquantite() ne verifie pas verifyCsrf().

Impact :
- modification possible sans protection CSRF serveur ;
- le token est affiche mais non utilise.

Correction recommandee :
- ajouter verifyCsrf() avant save($_POST) ;
- ajouter checkAuth() ;
- verifier que con_id appartient a la commande de l'utilisateur connecte.


5.5. Panier et commandes : propriete insuffisamment verifiee

Fichiers concernes :
- application/module/commande/Ctr_commande.class.php:93-117
- application/module/commande/Ctr_commande.class.php:120-132
- application/table/Commande.class.php:49-56
- application/table/Commande.class.php:59-67

Points positifs :
- selectCommandeByUtilisateurConnecter($id) filtre maintenant sur uti_id=:id.

Problemes restants :
- selectPanierByCommande($id) recupere un panier par id de commande sans
  verifier l'utilisateur ;
- a_commandeparutilisateur() ignore le parametre id du lien et utilise la
  session ;
- les actions edit, show et save de commande ne verifient pas toujours que la
  commande appartient a l'utilisateur ou que l'utilisateur est admin.

Correction recommandee :
- ajouter des methodes qui filtrent par commande ET utilisateur ;
- separer clairement les actions admin et les actions client ;
- pour un client, ne jamais faire confiance a un id commande fourni en URL.


5.6. Messages et sorties HTML non echappes

Fichiers concernes :
- application/gabarit/inc_message.php:3-5
- application/gabarit/inc_menu.php:25
- framework/Table.class.php:146-161
- application/module/*/vue_*_show.php:20

Probleme :
- inc_message.php affiche directement $message ;
- certains messages contiennent des valeurs utilisateur, par exemple email,
  prenom ou nom ;
- inc_menu.php affiche $_SESSION["uti_nom"] sans echappement ;
- Table::HTMLselect() genere des options sans echapper value et label ;
- les vues show affichent print_r($row), ce qui ressemble a du debug.

Impact :
- risque XSS si une valeur utilisateur contient du HTML/JS ;
- fuite d'informations techniques ;
- rendu peu professionnel.

Correction recommandee :
- afficher les messages avec mhe($message) ;
- echapper toutes les valeurs de session avant affichage ;
- echapper les options dans Table::HTMLselect() ;
- remplacer print_r($row) par un affichage propre ou retirer ces vues debug.


5.7. Mode development active

Fichiers concernes :
- .env:3
- framework/ErrorHandler.class.php

APP_ENV vaut development.

Probleme :
- en development, ErrorHandler affiche message, fichier, ligne et trace ;
- c'est utile localement mais dangereux en production.

Correction recommandee :
- utiliser APP_ENV=production sur un serveur public ;
- ne pas versionner les secrets ;
- garder .env local uniquement ;
- prevoir un .env.example sans mot de passe reel.


6. Qualite, maintenance et robustesse
-------------------------------------

6.1. Base de donnees

Fichier concerne :
- document/electromania.sql

Points positifs :
- schema clair ;
- cles etrangeres ajoutees ;
- statut separe dans une table ;
- utilisateur, profil, categorie, article, commande et contenir sont presents.

Points a ameliorer :
- uti_email n'a pas de contrainte UNIQUE ;
- art_prix est en FLOAT, mieux vaut DECIMAL(10,2) pour des prix ;
- plusieurs varchar(100) pourraient etre ajustes selon usage ;
- les contraintes n'ont pas de regle ON DELETE explicite ;
- les donnees de test utilisent des valeurs generiques.

Correction recommandee :
- ajouter UNIQUE(uti_email) ;
- remplacer FLOAT par DECIMAL(10,2) ;
- definir les politiques ON DELETE selon le besoin ;
- utiliser des INSERT avec noms de colonnes.


6.2. Dataset

Fichier concerne :
- document/dataset.php

Points positifs :
- password_hash() est utilise pour les utilisateurs de test ;
- l'ordre com_statut/com_utilisateur semble corrige par rapport a l'ancien etat.

Points a ameliorer :
- connexion MySQL hardcodee en root sans mot de passe ;
- mot de passe de test identique pour tous les utilisateurs ("mdp") ;
- insertions construites par concatenation ;
- aucune gestion d'erreur mysqli visible ;
- les donnees sont tres generiques.

Correction recommandee :
- utiliser la configuration .env ;
- utiliser les noms de colonnes dans les INSERT ;
- garder ce fichier uniquement pour l'environnement local ;
- afficher les erreurs de seed de facon claire.


6.3. Formulaires HTML

Fichiers concernes :
- application/module/article/vue_article_edit.php:31
- application/module/article/vue_article_recherche.php:22
- application/module/commande/vue_commande_edit.php:21
- application/module/commande/vue_commande_edit.php:26
- application/module/commande/vue_commande_panier.php:74

Problemes observes :
- attribut required parfois place dans le contenu du <select> ;
- attribut value utilise sur des <select>, ce qui n'est pas utile ;
- certains formulaires utilisent des labels techniques ;
- le formulaire d'ajout au panier n'apparait que si le panier n'est pas vide.

Correction recommandee :
- mettre required dans la balise <select> ;
- gerer la selection uniquement avec selected dans les <option> ;
- permettre l'ajout au panier meme si le panier est vide ;
- remplacer les libelles techniques par des libelles utilisateur.


6.4. Authentification et session

Fichiers concernes :
- application/module/authentification/ctr_authentification.class.php
- application/module/authentification/vue_authentification_inscription.php
- application/module/authentification/vue_authentification_connexion.php

Points positifs :
- password_hash() ;
- password_verify() ;
- token CSRF sur connexion et inscription ;
- profil client force a 1 lors de l'inscription.

Points a ameliorer :
- pas de session_regenerate_id(true) apres connexion ;
- deconnexion vide $_SESSION mais n'appelle pas session_destroy() ;
- pas de limite de tentatives de connexion ;
- message different si email inconnu ou mot de passe faux, ce qui facilite
  l'enumeration des comptes ;
- champ telephone pre-rempli avec mhe($uti_email) au lieu de la valeur telephone.

Correction recommandee :
- regenerer l'id de session apres connexion ;
- detruire proprement la session a la deconnexion ;
- utiliser un message generique de connexion echouee ;
- corriger la valeur de uti_numero_telephone dans la vue inscription ;
- ajouter required et type=email sur les champs adaptes.


6.5. Encodage

Constat :
- plusieurs sorties lues en console affichent des caracteres mal encodes
  comme "donnÃ©es" au lieu de "donnees" avec accents.

Cause probable :
- difference entre encodage des fichiers, terminal PowerShell et/ou fichiers
  historiques.

Correction recommandee :
- verifier que tous les fichiers texte/PHP sont en UTF-8 ;
- garder <meta charset="utf-8"> ;
- eviter de melanger plusieurs encodages.


7. Corrections prioritaires proposees
-------------------------------------

Priorite 1 - Securiser les routes sensibles :
- ajouter une liste blanche dans www/index.php ;
- bloquer _generateur hors local ;
- bloquer _default/creerbdd et _default/dataset hors local/admin ;
- verifier classe et methode avant appel.

Priorite 2 - Reprendre les autorisations :
- proteger chaque action admin avec checkAllow([3]) ;
- proteger chaque action client avec checkAuth() ;
- verifier la propriete des commandes et lignes de panier ;
- ne pas se fier au menu pour la securite.

Priorite 3 - Corriger les actions destructrices :
- convertir les delete en POST ;
- ajouter verifyCsrf() ;
- corriger commande/delete et la suppression de ligne panier ;
- verifier les statuts avant suppression.

Priorite 4 - Stabiliser le panier :
- utiliser $_SESSION["com_id"] pour la commande en cours ;
- passer art_id separement de com_id ;
- ajouter quantite via POST ;
- permettre l'ajout meme si le panier est vide ;
- corriger editquantite avec CSRF et controle de propriete.

Priorite 5 - Nettoyer les sorties :
- echapper les messages ;
- echapper les valeurs de session ;
- echapper Table::HTMLselect() ;
- retirer print_r($row) des vues show ;
- corriger les select HTML invalides.

Priorite 6 - Durcir la base :
- UNIQUE sur uti_email ;
- DECIMAL pour les prix ;
- .env.example ;
- APP_ENV=production en production ;
- seed local mieux separe.


8. Conclusion
-------------

ElectroMania est un projet pedagogique deja bien structure. Le socle MVC est
compris et plusieurs bonnes pratiques sont presentes, notamment les requetes
preparees dans les classes metier, le hachage des mots de passe et l'ajout
progressif de CSRF.

Le principal probleme n'est pas la structure generale, mais le niveau de
protection serveur. Beaucoup d'actions sont accessibles directement par URL et
les droits ne sont pas appliques partout. Avant d'ajouter de nouvelles
fonctionnalites, il faut donc securiser le routeur, les controleurs et les
actions de modification/suppression.

Une fois ces points corriges, le projet pourra devenir une base solide pour
continuer le panier, la validation de commande, le paiement fictif, le chiffre
d'affaires et les roles metier demandes dans le cahier des charges.
